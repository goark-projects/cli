# Code Generation

English | [简体中文](code-generation.zh-CN.md)

## Two Surfaces

Goark provides two distinct generation surfaces:

| Command | Intended use |
| --- | --- |
| `goark generate` | Normal project workflow: discover packages and regenerate all enabled Goark compile-time code. |
| `goark codegen ...` | Low-level tooling: generate one explicit artifact or scan one package with manually selected output. |

Neither command executes standard `//go:generate` directives. Use `goark go generate ...` for that behavior.

## Project Generation

```bash
goark generate
goark generate ./internal/...
goark generate -tags=integration ./...
goark generate --goark-profile=production
goark generate --goark-dry-run
```

The package set defaults to `[generate].patterns`, which defaults to `./...`. Discovery uses the official `go list` build file set and respects `-C`, `-tags`, `-mod`, `-modfile`, and `-overlay` where supplied.

The current annotation generator covers registration metadata for components, services, repositories, configurations, beans, injection points, conditions, Profiles, ordering, scopes, configuration properties, and Web/MVC declarations supported by the Goark generator packages.

## Output Ownership

Project outputs use:

```text
zz_goark_<package>_gen.go
```

Every successful generation rebuilds the complete file and atomically replaces the previous owned target. The required ownership line is:

```go
// Code generated by goark; DO NOT EDIT.
```

This provides three protections:

- Partial writes cannot publish a truncated target.
- Old generated declarations do not survive a successful regeneration.
- A same-named handwritten file is never silently overwritten.

With `clean-stale = true`, a package that no longer requires an output has its old file removed only when that header proves Goark ownership.

## Dry Run

`--goark-dry-run` performs discovery and planning but does not create, replace, or remove source files and does not execute lifecycle task processes.

```bash
goark generate --goark-dry-run
```

## Low-Level `annotations`

```text
goark codegen annotations --dir <package-dir> [flags]
```

| Option | Meaning |
| --- | --- |
| `--dir <path>` | Package directory; defaults to current directory. |
| `--package <name>` | Select package name when a directory contains multiple packages. |
| `--name <name>` | Configuration name used when no explicit configuration exists. |
| `--type <name>` | Configuration type used when no explicit configuration exists. |
| `--output <path>` | Write to a file instead of standard output. |

```bash
goark codegen annotations \
  --dir internal/app \
  --output internal/app/zz_goark_app_gen.go
```

## Low-Level `configuration`

```text
goark codegen configuration --name <name> --package <package> [flags]
```

It creates a `goark.Configuration` source file. Options include `--type`, `--order`, repeatable `--import`, repeatable `--bean`, and `--output`.

Bean grammar:

```text
name=provider[;deps=a,b][;scope=prototype][;lazy][;primary]
```

```bash
goark codegen configuration \
  --name user \
  --package generated \
  --bean "userRepository=NewUserRepository" \
  --bean "userService=NewUserService;deps=userRepository" \
  --output internal/generated/user_configuration.go
```

## Low-Level `registry`

```text
goark codegen registry --package <package> --configuration <type> [flags]
```

It generates a function that registers explicit configuration types. `--configuration` and `--import` are repeatable; `--function` changes the function name; `--output` writes the result.

```bash
goark codegen registry \
  --package generated \
  --import cfg=example.com/app/internal/config \
  --configuration cfg.AdminConfiguration \
  --output internal/generated/registry.go
```

## Choosing a Surface

- Use `goark generate` in development, CI, `run`, `build`, and `test` lifecycles.
- Use low-level `codegen` for generator development, explicit build tooling, or inspecting output on standard output.
- Use `goark go generate` only when the project intentionally executes standard Go generation directives and accepts their independent tools and side effects.
